# 01 · Struct Skeleton (Python port)

Python port of [`ruby/01_struct_skeleton`](../../ruby/01_struct_skeleton/README.md).
Built on top of the [`00_config`](../00_config/README.md) port — `Config`,
`Tasks.Base`, `Tasks.Player` carry over unchanged except `Config` drops the
`PROMPTS_DIR` constant here, matching this step's Ruby source exactly (see
"Differences from Ruby" below).

Let's define data structures for specific data we need to constantly pass around.
- `boukensha.Tool`
- `boukensha.Message`
- `boukensha.Context`

Ruby represents these as `Struct`s because they're lightweight and readable
for learning; in practice you'd probably use full classes. Python represents
them as `@dataclass`es for the same reason — `Tool`/`Message` are pure data,
`Context` is a regular class since it has real behavior beyond storage
(`register_tool`, `add_message`).

## Data Structures

### `Tool`
| Field | Description |
|---|---|
| `name` | The name of the tool |
| `description` | Shown to the agent so it knows when to invoke the tool |
| `parameters` | The arguments that need to be passed in |
| `block` | The actual code that runs when the tool is called |

**Examples:**
```
#<Tool name=move description=Move the player in a direction (north, south, east, west, up, down) params=['direction']>
#<Tool name=attack description=Attack a target in the current room params=['target']>
#<Tool name=look description=Look around the current room params=[]>
#<Tool name=say description=Say something out loud to others in the room params=['message']>
```

### `Message`
A single unit of conversation between the user and the agent.

| Field | Description |
|---|---|
| `role` | Who is speaking — user, assistant, or tool_result |
| `content` | The text generated by the agent or provided by the user |
| `tool_use_id` | Links a tool result back to the specific tool call that requested it. The API requires this pairing to be exact. |

**Examples:**
```
#<Message role=user content=Explore north and tell me what you find....>
#<Message role=assistant content=Sure, let me head north and take a look....>
#<Message role=tool_result [toolu_01X] content=You move north into a torch-lit corridor....>
```

### `Context`
Holds everything BOUKENSHA needs to make an API call. Nothing lives outside of this.

| Field | Description |
|---|---|
| `system` | Tells the agent what its job is. Sent as a separate field in the API call, never inside the messages array. |
| `messages` | The full conversation history, replayed on every turn |
| `tools` | The registered tools the agent is allowed to invoke |
| `token_budget` | How many tokens the run is allowed to consume (not read yet — added in a later step) |

```
#<Context task=player turns=2 tools=1>
```

## Run Example

```bash
./week1_baseline/bin/python/01_struct_skeleton
```

(or `./week1_baseline/bin/01_struct_skeleton --python` from the language-aware wrapper.)

## Differences from Ruby

- **No `PROMPTS_DIR`** — this step's `config.rb` upstream dropped the
  `PROMPTS_DIR` constant present in `00_config`, so `system_prompt` here only
  resolves a user override (`.boukensha/prompts/player/system.md`); there's
  no shipped default to fall back to. Ported as-is — not a Python-side
  choice, it's a genuine diff in the Ruby source between the two steps.
- **`role` stays a plain `str`** — Python's `typing.Literal["user",
  "assistant", "tool_result"]` could constrain `Message.role` to exactly
  those three values (something Ruby's untyped `Struct` can't express), but
  we deliberately kept it loose for 1:1 parity with Ruby.
- Carries forward the standing decisions from `00_config`: `.yaml`/`.yml`
  fallback fix (Python-side only), no pytest suite, `uv`/hatchling,
  `requires-python >=3.14`.
